# RecoverOS v2 — Implementation Contract

**This document is the authoritative build spec. `PLAN.md` is the strategy/pitch narrative and must not be treated as implementation instructions.**

Read §1 before writing any code. Every constant in this document is deliberate. Do not substitute your own.

## 1. Rules For The Implementing Agent

These are invariants. Breaking any one of them silently invalidates the submission's core claim, because the whole product rests on results being reproducible.

### 1.1 Hard rules

| # | Rule | Why |
|---|---|---|
| **I1** | **Never call `Math.random()` in `lib/`.** All randomness comes from a seeded PRNG passed in explicitly (§3.2). | Reproducibility is the product. One stray `Math.random()` and the eval harness stops being deterministic. |
| **I2** | **Never call `Date.now()` or `new Date()` in `lib/`.** Time comes from an injected `Clock` (§3.3). | Replay and time-compressed demo both require controllable time. |
| **I3** | **All money is integer paise.** Never float. Type is `Paise = number` and it must always hold an integer. | Float accumulation across 50,000 episodes produces drifting totals that judges may notice. |
| **I4** | **Never mutate a `RecoveryEpisode` in place.** All state changes go through `transition()` in `lib/state-machine.ts`, which returns a new object. | The audit trail must be complete. |
| **I5** | **Every state transition emits exactly one `AuditEvent`.** No transition without an audit row. | Bar requirement. |
| **I6** | **Never widen the action set.** It is exactly the 7 actions in §3.1. New behaviours are new *states*, not new actions. | "Bounded" is a judged property. |
| **I7** | **Executors are pure-idempotent by `idempotencyKey`.** Second call with the same key returns the first result, never re-executes. | Already true; do not regress it. |
| **I8** | **No network calls in eval/replay code paths.** Ever. | `npm run eval` must work offline and finish in bounded time. |
| **I9** | **Do not add auth, OAuth, multi-tenancy, Redis, BullMQ, or an ORM.** If a task seems to need one, the task is being misread. | Explicitly out of scope. See `PLAN.md` §3. |
| **I10** | **Do not edit `RESULTS.md` by hand.** It is generated by `npm run eval`. | Hand-edited results are fraud, and a judge who spots it ends your submission. |

### 1.2 Working rules

- **One task at a time, in the order given in §2.** Each task has a Definition of Done that is a shell command. Do not start task N+1 until task N's DoD command exits 0.
- **If a type doesn't exist yet, create it in `lib/domain.ts` as a Zod schema and export the inferred type.** Do not define ad-hoc interfaces in feature files.
- **If this spec and existing code disagree, this spec wins** — except for I1–I10, which nothing overrides.
- **If a required constant is not in this document, stop and ask.** Do not invent thresholds.

### 1.3 Known failure modes — read this twice

These are the specific mistakes an implementing agent is most likely to make here.

1. **Randomising the wrong population.** The holdout coin flip happens *after* eligibility is decided, not before. See §5.3. Getting this backwards silently destroys the headline number.
2. **Poisoning the degradation baseline with outage data.** The EWMA baseline must **not** update while a degradation window is open. See §7.4.
3. **Confusing "low EIR" with "negative EIR".** `WAIT` and `SUPPRESSED` are different states with different ledgers. See §8.5.
4. **Using across-seed variance where bootstrap is required, or vice versa.** They answer different questions. See §4.6.
5. **Letting `SUPPRESSED` or `HELD_DEGRADED` episodes enter the experiment.** They are not action-eligible. See §5.3.
6. **Reusing `WAIT` for the new restraint states.** Each restraint reason needs its own state or the demo can't distinguish them.
7. **Formatting money in engine code.** Paise integers throughout; format only in React components.

### 3.2 Seeded PRNG — `lib/rng.ts` (new file)

Use **mulberry32**. Do not substitute another algorithm; the eval outputs are checked against committed values.

```ts
// lib/rng.ts
export interface Rng {
  next(): number;          // uniform [0, 1)
  int(maxExclusive: number): number;
  pick<T>(items: readonly T[]): T;
  bernoulli(p: number): boolean;
}

export function mulberry32(seed: number): Rng {
  let a = seed >>> 0;
  const next = () => {
    a = (a + 0x6D2B79F5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
  return {
    next,
    int: (maxExclusive) => Math.floor(next() * maxExclusive),
    pick: (items) => items[Math.floor(next() * items.length)],
    bernoulli: (p) => next() < p,
  };
}
```

**Test (`tests/rng.test.ts`):** `mulberry32(42).next()` called 3 times produces the same 3 values on every run. Assert against literal values captured on first run.

### 3.3 Clock — `lib/clock.ts` (new file)

```ts
// lib/clock.ts
export interface Clock { now(): number; }                 // epoch millis

export function systemClock(): Clock {
  return { now: () => Date.now() };
}

export function fixedClock(startMs: number, stepMs = 0): Clock {
  let t = startMs;
  return { now: () => { const v = t; t += stepMs; return v; } };
}

/** Demo/simulation clock: advances `speed`× faster than wall time. */
export function scaledClock(startMs: number, speed: number): Clock {
  const origin = Date.now();
  return { now: () => startMs + (Date.now() - origin) * speed };
}
```

Every engine function that needs time takes `clock: Clock` as an explicit parameter. No module-level clock singletons.

### 3.4 Money — `lib/money.ts` (new file)

```ts
// lib/money.ts
export type Paise = number;   // ALWAYS an integer

export const rupees = (r: number): Paise => Math.round(r * 100);
export const toRupees = (p: Paise): number => p / 100;

export function formatInr(p: Paise): string {
  return new Intl.NumberFormat('en-IN', {
    style: 'currency', currency: 'INR', maximumFractionDigits: 0,
  }).format(p / 100);
}

/** Multiply paise by a probability/rate. Rounds to integer paise. */
export function scale(p: Paise, rate: number): Paise {
  return Math.round(p * rate);
}

export function assertPaise(p: number, label: string): void {
  if (!Number.isInteger(p)) throw new Error(`${label} must be integer paise, got ${p}`);
}
```

### T4 · Simulator ground truth + sweep

**File:** `lib/simulator.ts`, `lib/eval/sweep.ts`, `SIMULATOR.md`

Every synthetic episode carries hidden truth, never visible to the engine:

```ts
export interface GroundTruth {
  pNativeTrue: number;                    // recovers with no action
  pActionTrue: Record<Action, number>;    // recovers given each action
  willChurnIfContacted: boolean;          // for dormancy validation
  issuerDegraded: boolean;                // was this an outage failure
}
```

**Outcome resolution** — the only place outcomes are decided:

```ts
export function resolveOutcome(
  truth: GroundTruth, action: Action, rng: Rng
): { recovered: boolean; churned: boolean } {
  const p = action === 'WAIT' ? truth.pNativeTrue : truth.pActionTrue[action];
  return {
    recovered: rng.bernoulli(p),
    churned: action !== 'WAIT' && truth.willChurnIfContacted,
  };
}
```

> `HELD_OUT`, `HELD_DEGRADED` and `SUPPRESSED` episodes resolve with `action = 'WAIT'`. That is what makes the control arm a true counterfactual.

**Planted incremental value** (ground truth for validating the estimator):

```
plantedIncrementalPaise = Σ over action-eligible episodes:
    (pActionTrue[chosenAction] − pNativeTrue) × amountPaise
```

#### 4.6 Statistics — get this right

Two different intervals, for two different questions. **Do not interchange them.**

| Question | Method | Where |
|---|---|---|
| "Does RecoverOS beat the other arms?" | **Across-seed**: mean ± t-interval over the *N seeds*, df = N−1 | `aggregate` in `EvalReport` |
| "How much incremental value did the holdout measure?" | **Bootstrap**: resample *episodes* within a run, 10,000 resamples, percentile 2.5/97.5 | `HoldoutResult` |

```ts
// lib/eval/estimators.ts
export function tInterval(values: number[], confidence = 0.95): AggregateStat;
export function bootstrapCi(
  treatment: EpisodeOutcome[], holdout: EpisodeOutcome[],
  resamples: number, rng: Rng
): { pointPaise: Paise; loPaise: Paise; hiPaise: Paise };
```

Bootstrap must use the injected `rng` (I1), so CIs are reproducible.

**Sweep** (`npm run eval:sweep`): vary each assumption over a 5-point grid holding others at default; emit a matrix of `netPaise(RECOVEROS) − netPaise(BASELINE)`. **Identify and report every cell where the value is ≤ 0.** That table goes in `RESULTS.md` under a heading literally called *"Where we stop winning."*

**DoD:** `npm run eval:sweep` produces a table containing at least one non-winning cell. If none exists, widen the grid until one does — a product that wins under every conceivable assumption is not being tested honestly.

## 5. T6 · Holdout Ledger

### 5.1 `lib/experiment.ts`

```ts
export const EXPERIMENT_SALT = 'recoveros-v1';
export const SALT_VERSION = 'v1';

/** FNV-1a 32-bit. Deterministic across Node and browser. Do not substitute. */
export function hashToBucket(input: string): number {
  let h = 0x811c9dc5;
  for (let i = 0; i < input.length; i++) {
    h ^= input.charCodeAt(i);
    h = Math.imul(h, 0x01000193) >>> 0;
  }
  return h % 100;                    // 0..99
}

export function assignArm(episodeId: string, holdoutPct: number): ExperimentArm {
  if (holdoutPct <= 0) return 'TREATMENT';
  return hashToBucket(episodeId + EXPERIMENT_SALT) < holdoutPct
    ? 'HOLDOUT' : 'TREATMENT';
}
```

Hash-based, **not** RNG-based, so the same episode always lands in the same arm regardless of processing order or replay.

### 5.2 Constants

| Constant | Value | Notes |
|---|---|---|
| `HOLDOUT_PCT` | `5` | env-overridable, `0` disables |
| `HOLDOUT_VALUE_CAP_PAISE` | `rupees(50_000)` | above this, never hold out |

### 5.3 Assignment point — **the most important 12 lines in the build**

In `lib/policy.ts`, inside `evaluatePolicy()`, in exactly this order:

```
1. Run ALL existing policy gates (consent, opt-out, contact window,
   attempt caps, native recovery state, voice budget, EIR threshold).
2. Run the degradation gate (§7.5) and the suppression gate (§8.5).
3. IF the resulting decision is NOT to act (WAIT / STOP / SUPPRESSED /
   HELD_DEGRADED):
       → eligible = false
       → arm = undefined          ← DO NOT ASSIGN AN ARM
       → return decision unchanged
4. ELSE (we would genuinely have acted):
       → eligible = true
       → if amountPaise > HOLDOUT_VALUE_CAP_PAISE: arm = 'TREATMENT'
       → else arm = assignArm(episodeId, HOLDOUT_PCT)
5. IF arm === 'HOLDOUT': override action to no-op, status = HELD_OUT,
   emit audit EXPERIMENT_ASSIGNED, and DO NOT execute.
6. ELSE: proceed to execution as normal.
```

**Why step 3 matters.** If you flip the coin on all episodes rather than only action-eligible ones, the control arm fills with cases where treatment would never have happened. Both arms then contain mostly untreated episodes, the measured difference collapses toward zero, and the headline number — the entire submission — reads as near-worthless. This is the single highest-consequence bug in the project.

The value cap in step 4 is deliberate: withholding recovery on a ₹50,000+ failure to improve a statistic is not a trade a real merchant would accept.

### 5.5 Estimator output

```ts
export interface HoldoutResult {
  nTreatment: number;
  nHoldout: number;
  recoveryRateTreatment: number;

```

```

### 5.6 Self-validation test — `tests/holdout-estimator.test.ts`

```

## 7. T8 · Issuer Degradation Detector

**File:** `lib/degradation.ts`

### 7.1 Constants — do not tune these ad hoc

| Constant | Value | Meaning |
|---|---|---|
| `WINDOW_MS` | `15 * 60 * 1000` | tumbling window |
| `EWMA_ALPHA` | `0.1` | baseline smoothing |
| `TRIGGER_RATIO` | `3.0` | fire when observed ≥ 3× baseline |
| `MIN_ATTEMPTS` | `20` | per window, per key — small-sample guard |
| `MIN_ABSOLUTE_RATE` | `0.15` | never fire below this failure rate |
| `CLOSE_RATIO` | `2.1` | = `TRIGGER_RATIO × 0.7`, hysteresis |
| `CLOSE_WINDOWS` | `2` | consecutive windows below `CLOSE_RATIO` |
| `DRAIN_JITTER_MS` | `120_000` | spread requeues over 2 min |
| `BASELINE_SEED_WINDOWS` | `8` | warm-up before detector may fire |

### 7.2 Key

```ts
export function degradationKey(e: PaymentEvent): string {
  return [e.method, e.issuer ?? '-', e.network ?? '-'].join('|');
}
```

### 7.3 Window accounting

```ts
export interface WindowCounter { attempts: number; failures: number; }

export class DegradationDetector {
  constructor(private clock: Clock, private store: RecoveryStore) {}
  record(e: PaymentEvent, failed: boolean): void;
  /** Call at each window boundary. Returns windows opened/closed. */
  tick(): { opened: DegradationWindow[]; closed: DegradationWindow[] };
  isDegraded(key: string): DegradationWindow | null;
}
```

### 7.4 Detection algorithm — exact

```
On tick() for each key:
  rate = failures / attempts        (0 if attempts === 0)

  IF window is currently OPEN for this key:
      ratio = rate / baseline
      IF ratio < CLOSE_RATIO: consecutiveBelow += 1
      ELSE consecutiveBelow = 0
      IF consecutiveBelow >= CLOSE_WINDOWS:
          close window, set closed_at_ms, emit 'closed'
      # ⚠ DO NOT UPDATE BASELINE WHILE OPEN
  ELSE:
      baseline = EWMA_ALPHA * rate + (1 - EWMA_ALPHA) * baseline
      seenWindows += 1
      IF seenWindows >= BASELINE_SEED_WINDOWS
         AND attempts >= MIN_ATTEMPTS
         AND rate >= MIN_ABSOLUTE_RATE
         AND baseline > 0
         AND rate / baseline >= TRIGGER_RATIO:
             open window, emit 'opened'

  reset counters for next window
```

**The baseline-freeze rule is not optional.** If the EWMA keeps updating during an outage, the baseline climbs toward the outage rate, the ratio decays toward 1.0, and the window closes while the issuer is still down — the detector quietly cancels itself. This is the classic implementation bug for this pattern.

### 7.5 Policy gate

In `evaluatePolicy()`, **before** the experiment assignment (§5.3 step 2):

```
window = detector.isDegraded(degradationKey(event))
IF window !== null:
    decision.action = 'WAIT'
    decision.status = 'HELD_DEGRADED'
    decision.degradationWindowId = window.id
    decision.reason = `Issuer degradation: ${key} at ${ratio}× baseline`
    increment window.episodesHeld
    emit audit DEGRADATION_HELD
    → no contact, no retry attempt consumed, episode NOT counted
      against attempt caps
```

**On window close:** requeue every `HELD_DEGRADED` episode for that window back to `POLICY_CHECK`, each scheduled at `now + rng.int(DRAIN_JITTER_MS)`. Emit `DEGRADATION_RELEASED`. Jitter prevents a thundering herd against a bank that just came back up.

### 7.6 Tests — `tests/degradation.test.ts`

| Test | Assertion |
|---|---|
| `does not fire below MIN_ATTEMPTS` | 19 attempts at 100% failure → no window |
| `does not fire on high-but-stable baseline` | steady 20% rate for 20 windows → no window |
| `fires on 4× spike` | baseline 5%, spike to 20%, 30 attempts → window opens |
| `baseline does not drift during outage` | 10 windows of outage → `baselineRate` unchanged from pre-outage value |
| `closes with hysteresis` | rate returns to baseline → closes after exactly 2 windows, not 1 |
| `held episodes consume no attempts` | `automatedAttempts` unchanged for `HELD_DEGRADED` |

## 8. T9 · Dormancy Suppression

**File:** `lib/scoring.ts`

### 8.1 Extended EIR

```
eirWithoutChurnPaise = scale(amountPaise, pAction − pNative) − costPaise
churnCostPaise       = scale(residualLtvPaise, deltaPChurn)
eirPaise             = eirWithoutChurnPaise − churnCostPaise
```

All three are stored on `EIRScore` (§T2) because the suppression classifier needs to compare them.

### 8.2 Residual LTV

```ts
export function residualLtv(profile: CustomerProfile, amountPaise: Paise): Paise {
  if (!profile.isSubscription) return 0;
  const expectedRemainingPeriods = Math.min(
    12, Math.max(0, 12 - Math.floor(profile.daysSinceLastSuccess / 30))
  );
  return amountPaise * expectedRemainingPeriods;
}
```

### 8.3 Dormancy churn curve

Piecewise linear on `daysSinceLastEngagement`. Interpolate between points; clamp outside.

| Days dormant | `deltaPChurn` |
|---|---|
| 0 | 0.00 |
| 30 | 0.00 |
| 60 | 0.01 |
| 120 | 0.04 |
| 180 | 0.09 |
| 365 | 0.15 |

```ts
export const DORMANCY_CHURN_CURVE: [number, number][] =
  [[0, 0.0], [30, 0.0], [60, 0.01], [120, 0.04], [180, 0.09], [365, 0.15]];
```

Applies **only** when `profile.isSubscription === true` **and** the action is a contact action (`REMINDER`, `VOICE_CALL`, `PAYMENT_LINK`). `RETRY` and `WAIT` carry no churn cost — a silent retry doesn't remind anyone of anything.

> `deltaPChurn` is the least empirically grounded parameter in the system. It **must** appear in the sweep (§4.5) and be flagged in `RESULTS.md`.

### 8.4 `daysSinceLastEngagement`

Add to `CustomerProfile`. If real engagement data is unavailable, fall back to `daysSinceLastSuccess` and set `engagementProxy: true` on the profile so the UI can label it honestly.

### 8.5 Suppression classifier — read carefully

```
IF eirPaise < 0 AND eirWithoutChurnPaise >= policy.eirThresholdPaise:
    → status = SUPPRESSED, reason = 'DORMANCY_CHURN_RISK'
       (we WOULD have acted, but the churn cost makes it destructive)

ELSE IF eirPaise < 0:
    → status = SUPPRESSED, reason = 'NEGATIVE_EIR_OTHER'

ELSE IF eirPaise < policy.eirThresholdPaise:
    → action = 'WAIT'    (ordinary low-value case — NOT suppression)

ELSE:
    → proceed to proposal
```

`WAIT` and `SUPPRESSED` must never be merged. `WAIT` means "not worth it"; `SUPPRESSED` means "actively harmful". Only the second feeds the Protected ledger.

### 8.6 Protected ledger

Report **both** numbers, never just the flattering one:

```
protectedPaise = Σ over SUPPRESSED episodes of churnCostPaise
forgonePaise   = Σ over SUPPRESSED episodes of max(0, eirWithoutChurnPaise)
```

UI shows: `Protected ₹X · Forgone ₹Y · Net ₹(X−Y)`.

### 8.7 Tests — `tests/suppression.test.ts`

| Test | Assertion |
|---|---|
| `dormant low-value subscription is suppressed` | ₹499, 150 days dormant → `SUPPRESSED / DORMANCY_CHURN_RISK` |
| `active subscription is not suppressed` | ₹499, 5 days dormant → proceeds |
| `high-value dormant still acts` | ₹50,000, 150 days dormant → proceeds (amount dominates churn cost) |
| `RETRY carries no churn cost` | `churnCostPaise === 0` for `RETRY` |
| `low EIR is WAIT not SUPPRESSED` | `eirWithoutChurn` below threshold, no churn → `WAIT` |
| `one-off payment has zero residual LTV` | `isSubscription: false` → `residualLtvPaise === 0` |

### 10.1 Outcome resolution during replay — the honesty rule

```
For each replayed episode:
  IF replayed action === action actually taken:
      → use the OBSERVED outcome (real data)
  ELSE:
      → use model.predict(diagnosis, action, profile)  (modelled)
```

Track `observedFraction` and **display it in the UI**: `"63% of these outcomes are observed; 37% are modelled."` Not a buried disclaimer — a visible footnote on the panel.

### 10.2 Model calibration — where the mechanics compose

```ts
model.predict(diagnosisCategory, action, profile) =
   (recoveries + 1) / (attempts + 2)      // Laplace smoothing
   bucketed by (diagnosisCategory × action)
   fallback to global prior when attempts < 30
```

**Calibrate `action = WAIT` from the HOLDOUT arm.** That is real, unconfounded counterfactual data — the holdout is what makes the replay defensible rather than fabricated. Say this in the pitch.

**DoD:** replaying with the *unchanged* policy yields all deltas within ±0.5% of zero. If it doesn't, replay is not faithful and something is nondeterministic.
